What this guide does and does not claim

The engine already supports imported scenes, rendering, Jolt physics, character movement, skeletal animation, Lua scripts, and development tools. The intended game is a PC arena showdown game with Blender as its level editor.

The current source does not contain a complete multiplayer stack, world streaming system, audio system, or RmlUI integration. Ten-player online matches, full Haki combat, and a finished game UI remain game and engine work ahead. An architecture explanation should not make those sound finished.

When updating a system, update its chapter and any examples that cross into another system. For a new component, use the feature checklist.

1. The big picture

Haki takes a scene you author in Blender, converts it into files the engine understands, and runs it with C++, Lua, OpenGL, and Jolt.

Think of a scene as the contents of one playable place: its floor, walls, player, camera, lights, and rules. The engine provides the systems that make those things work. Your game supplies the particular objects, artwork, and rules.

The full journey

In words: Blender authors the scene; Python prepares its runtime files; C++ loads those files into a live scene; simulation changes that scene; the renderer draws its current state.

There are two different kinds of import here. The Python importer prepares files on disk. The runtime loaders read those prepared assets into memory. Neither step runs Blender inside the engine.

The main boundaries

Part Its responsibility Where it lives
Engine General systems such as rendering, physics, assets, and scripting src/Haki/
Game Arenas, characters, materials, and game rules Assets/Game/
Engine defaults Reusable shaders, primitive geometry, fonts, default environment Assets/Engine/
Authoring Object placement, colliders, script assignment, and export settings Blender and tools/blender/haki_editor/
Import tools Validate exports and create scene packages tools/import_gltf_pack.py
Tests Check individual systems and pipeline behavior src/Tests/ and tools/tests/

For example, deciding that a punch deals 20 damage belongs in game logic. Providing a sphere query that finds nearby physics objects belongs in the engine. This keeps the engine reusable for your next game.

The runtime has a small chain of ownership

Game owns the window, renderer, and scene manager. SceneManager owns one active scene. That scene owns its entity storage, physics world, and Lua script system. Loaded assets live in a shared asset manager, outside a particular scene.

Ownership means responsibility for creating, keeping, and destroying a thing. If a scene owns its physics world, leaving that scene should remove that world and its bodies. A model resource can remain loaded because the asset manager owns it separately.

The engine mostly uses C++ objects to manage these lifetimes. A std::unique_ptr<Scene> means there is one owner of that scene. A std::shared_ptr<AssetCatalog> means several systems refer to the same catalog and keep it alive together. These are memory ownership tools, not asset file formats.

How an object gets behavior

An object in the scene is an entity. An entity is an identifier with attached pieces of data called components.

A floor can have a transform, a mesh renderer, a rigid body, and a collider. A camera can have only a transform and camera component. A player controller can have a transform, character controller, and script, while its animated visual is a separate child entity.

A system reads matching components and performs work. Physics looks for physics components. Animation looks for skinned meshes and animators. Rendering looks for visible geometry and materials.

This pattern is called an entity-component system, or ECS. Here it is built using EnTT. The name is less important than the idea: objects are made by combining data, rather than putting every possible behavior into one huge GameObject class.

Haki still decides how these libraries cooperate. Jolt does not know what a Haki scene file is. OpenGL does not know which Blender object is the player. Those connections are engine code.

Current strengths and current limits

The present structure is well suited to building and testing a small arena: authored maps, a controlled player, animation, Lua behaviors, physics queries, and adjustable graphics.

Scene changes currently load synchronously: the main thread does the loading work. Registering many scenes does not mean they are all loaded. There is no background world streaming service in this code.

Jolt uses worker threads for parts of physics. This does not make EnTT, Lua, the asset manager, or OpenGL safe to access from arbitrary worker threads. A general engine job system and network simulation architecture would require additional design.

2. Startup and the frame loop

A game program repeats two jobs: update the world and draw a picture of it. Haki updates the world at a fixed rate and draws as often as the outer loop allows.

What happens at startup

main() installs a console logger, constructs Game, and calls Run(). The default project path is Assets/Game/Project.json.

Project settings load before the window is created. That lets saved dimensions, title, and window mode take effect from the start.

Game::InitializeSystems() then prepares the engine in this order:

  1. Confirm that the window and OpenGL context are usable.
  2. Start the asset manager and register its loaders.
  3. Start the shared Jolt support through PhysicsCore.
  4. Connect input to the window.
  5. Create renderer resources.
  6. Load fonts and prepare telemetry.
  7. Start the optional ImGui development interface.
  8. Read the project scene manifest, register scene factories, and request the entry scene.

A context here is the connection between this thread and the OpenGL state for the window. GPU objects such as textures cannot be created before this is ready.

Registering a scene stores a way to create it later. The entry scene becomes active when the scene manager processes its request during an update.

A frame and a tick are different

A rendered frame is one picture presented to the window. A simulation tick is one step of gameplay and physics.

Haki's fixed tick is 1 / 60 second, about 16.67 milliseconds. The drawing rate can be higher or lower.

At 120 rendered frames per second, some frames have no simulation step. At 30 rendered frames per second, a frame will commonly perform two simulation steps. Those are examples of normal timing, not promises about exact scheduling.

This helps physics because it sees a regular time step. It also makes gameplay easier to reason about: movement speed is measured in units per second instead of units per picture.

distance = speed × seconds
5 metres/second × 1/60 second = about 0.083 metres per tick

The accumulator

The main loop keeps an amount of unprocessed simulation time called an accumulator.

measure time since the last frame
add a capped amount of that time to the accumulator

while at least one fixed step remains, up to 8 steps:
    update the scene by 1/60 second
    subtract 1/60 second

draw once

The code caps a single frame's added simulation time at 0.25 seconds. It also limits catch-up work to 8 ticks per frame, then discards excess whole steps. Otherwise one slow frame could cause so much catch-up work that the engine never recovers.

That means a very large stall can make simulation time fall behind real time. This is a deliberate limit on work, not a network rollback system. The loop currently does not interpolate between two physics snapshots when drawing.

What happens in one outer frame

The simplified order in Game::Run() is:

  1. Measure elapsed time and poll window events.
  2. Update input once.
  3. Build the editor UI, handle its requests, and check project setting saves.
  4. Decide whether gameplay or the debug camera owns input.
  5. Run zero or more fixed simulation ticks.
  6. Update the optional free-look camera for this rendered frame.
  7. Poll shader and script files for changes.
  8. Queue telemetry, render the scene, and draw ImGui on top.
  9. Swap the window buffers to present the picture.

Buffer swapping makes the completed image visible while the next image is drawn elsewhere. It avoids showing a half-drawn frame.

The order inside one simulation tick

The main loop first runs PlayerControllerSystem::Update(). This can fill desired movement from built-in player input. SceneManager::Update() then advances scene transitions and calls the scene's OnUpdate() and UpdateRuntime().

Within Scene::UpdateRuntime() the order is:

Stage What it does Why the order matters
Prepare scene systems Lazily create physics and Lua support when needed Components need runtime systems before they can act
Lua update Start new scripts and run gameplay callbacks Scripts can request movement before physics
Physics Create pending bodies, move controllers, step Jolt, copy results back Collision decides the movement that really happened
Contact callbacks Deliver collision and trigger events to scripts Events now describe the completed physics step
Transform hierarchy Move attached children with their parents A visual follows the controller's corrected position
Animation Evaluate clips and locomotion Locomotion can use actual speed after collision

A camera moved from Lua's on_update sees the player's state before that tick's physics step. If you investigate subtle camera lag, this order is one place to look. A future dedicated post-physics gameplay phase would be a new feature.

The base C++ Scene::OnUpdate() is empty. Engine systems run through UpdateRuntime(), so a scene subclass does not have to call those systems itself.

Pausing

When simulation is paused, the runtime step uses a delta time of zero unless a single step was requested. Scripts do not advance, contacts are not dispatched again, and physics does not simulate.

Physics can still create newly added bodies. Transform and animation evaluation still run with zero time so the scene can remain visible and editable. Drawing also continues. Lua on_draw receives zero time while paused.

Input timing matters

Input is sampled once per outer frame. Several catch-up ticks can therefore see the same sampled state. A call such as input.key_pressed() is a frame edge, not a separately consumed event for each simulation tick.

For held movement this is normally fine. For actions such as firing once per press, use an explicit action/cooldown policy and be aware of catch-up ticks. Do not assume the engine already has a queued input command for every simulation tick.

Shutdown and lifetime

The active scene shuts down before shared physics support is destroyed. Renderer and asset GPU resources are released while the window's OpenGL context still exists. Input disconnects before the window disappears.

This is why member order and shutdown order matter. Calling glDeleteTextures after destroying the OpenGL context would be a lifetime error even if the texture's C++ destructor itself looked correct.

3. Entities, transforms, and cameras

The scene's EnTT registry stores its live objects. Systems ask that registry for entities with the components they need.

Entity, component, and system

An entity is a runtime identifier. A component is data attached to it. A system is code that uses some combination of components.

This small C++ example shows the pattern. It is a teaching example, not a replacement for scene loading:

auto entity = registry.create();
registry.emplace<Haki::TransformComponent>(entity);
registry.emplace<Haki::NameComponent>(entity, "Test object");

auto view = registry.view<Haki::TransformComponent>();
for (auto e : view)
{
    auto &transform = view.get<Haki::TransformComponent>(e);
    transform.Translation.x += 1.0f;
}

A view means “give me the entities with these components.” A view of transform plus mesh renderer leaves out cameras and invisible triggers automatically.

Three kinds of identity

Identity Example Purpose
Authored entity ID A UUID stored by the add-on, or player in a small test Stable references across exported scene files
Runtime entity handle entt::entity Access to one live entity in one registry
Name Player, Fence, Camera Human-readable display and convenient lookups

EntityIdComponent stores the authored ID. NameComponent stores the display name. Names can repeat, so use stable IDs when a relationship must be unambiguous.

Do not write a runtime entity handle into a scene file and expect it to identify the same object next run. Reloading a scene creates a new registry and new runtime objects.

Component Data it carries

Not every entity needs every component. An invisible collider is useful precisely because it has physics without a rendered mesh.

Position, rotation, and scale

A transform describes where something is, how it is turned, and how large it is.

The engine uses Y as up. The ground is normally the XZ plane. A camera's forward direction is local negative Z. The player-facing math also treats negative Z as forward.

The Blender export converts Blender's Z-up coordinates to the engine/glTF Y-up convention. In the usual conversion, (x, y, z) becomes (x, z, -y). Do not manually apply that conversion again to an already exported scene.

Use metres consistently for scene dimensions. Jolt's gravity is (0, -9.81, 0), and the default controller is about 1.8 units tall. A metre-based scale makes movement and camera framing easier to tune together.

What a matrix does

A matrix is a compact way to combine several transform operations. The engine builds an object's world matrix as:

World = Translation × Rotation × Scale

With the math convention used here, a vertex gets scaled first, then rotated, then translated. The result puts the mesh's own coordinates into world coordinates.

What a quaternion does

A quaternion stores a rotation without relying on three independently edited Euler angles. You can understand it as a rotation value; you do not need to memorize its four-number math to use it.

Scene JSON stores it as [x, y, z, w]. GLM's quaternion constructor takes (w, x, y, z). The parser deliberately changes the order. The identity rotation is [0, 0, 0, 1] in JSON.

Lua rotation helpers use radians. A half-turn is math.pi; a quarter-turn is math.pi / 2. Camera FOV settings and physics slope settings are named in degrees instead.

A player is usually more than one entity

Player controller entity
  Transform: feet position and gameplay facing
  CharacterController: capsule and movement
  Script: player behavior

  Character visual entity
    ParentTransform: attached to Player
    Local transform: model fit and forward correction
    SkinnedMeshRenderer + Animator + LocomotionAnimation

The controller should remain upright and have predictable dimensions. The visual may need a local rotation or scale adjustment because of the downloaded model's original authoring conventions.

Keeping that correction on the visual avoids rotating movement axes or lying about capsule size. An armature is the animation skeleton; it does not automatically become the gameplay controller.

The add-on offers attachment controls for this relationship. The runtime uses explicit parent metadata, rather than preserving every organizational Blender parent as a gameplay relationship.

How runtime parenting works

For an attached child:

child world matrix = parent world matrix × child local matrix

TransformHierarchySystem finds parents using stable IDs and evaluates parents before children. It updates each child's world matrix and world transform values. Its ParentTransformComponent.Local remains the relative transform used to rebuild that result.

This means changing a child's world position alone is not a lasting local edit: the next hierarchy update derives it again from the parent and local transform.

Physics bodies and character controllers are required to be world roots in the authored runtime hierarchy. Attach visuals to the controller; do not make the controller a child of an animated mesh. This avoids two systems competing to decide its world position.

The imported scene can be mostly flat while a skeleton still keeps its own bone hierarchy. These are separate hierarchies with different jobs.

What the camera actually does

The renderer uses three spaces:

mesh coordinates → world coordinates → camera coordinates → projected screen position

The view matrix is the inverse of the camera's world transform. It describes the world as seen from that camera. The projection matrix decides how that view becomes a 2D image.

Projection Result Main size control
Perspective Farther objects appear smaller Vertical FOV and camera position
Orthographic Distance does not change apparent object size OrthographicSize

OrthographicSize is half the visible height, not the whole width or height. If it is 6, the camera view spans 12 units vertically in camera space. At 16:9, the width is about 21.33 units. A steep camera pitch changes how this rectangle meets the ground.

For a Brawl Stars-like composition, pitch, projection, view size, object dimensions, and player size all contribute. Moving an orthographic camera farther away does not zoom out the way a perspective camera does.

Exactly one camera must be marked primary in a serialized scene. The primary camera is the gameplay view. The development free-look camera and projection override are separate views and can make the runtime appear different without changing the authored camera component.

4. Files, serialization, and scene management

Serialization means turning structured program data into a form that can be stored or sent. Deserialization means reading that form and rebuilding useful program data from it.

For Haki, JSON describes a scene. Loading creates C++ components, resolves assets, and builds a live Scene. It does not copy a block of raw C++ memory from disk.

Why the file cannot just contain a C++ object

A live component may contain an asset handle or a reference to a Jolt body. Those values are meaningful only in the running program that created them. A memory address from yesterday's run is useless today.

The stored version uses stable information instead: entity IDs, asset IDs, numbers, and script paths. Loading turns those stable descriptions into new runtime objects.

For example:

On disk: mesh = "engine.mesh.unit-cube"
Load: find catalog entry → load resource if needed
In memory: MeshHandle { Index, Generation }

The files have different jobs

File Question it answers
Game/Project.json Which scenes exist, which starts first, and what are the project window/render settings?
Scene .scene.json Which entities and components make up this scene?
Catalog.json Where is each named asset, and what type is it?
.material.json Which shader, parameters, textures, and draw state does a material use?
.prefab.json Which reusable entity description should be expanded into a scene?
ImportReceipt.json Which output files belong to this import operation?
.blend Editable Blender source
.glb / .gltf Exported meshes, materials, skeletons, clips, and related model data
.lua Gameplay behavior

A schema is the set of fields and rules a file format accepts. Haki checks headers such as "type": "haki.scene" and "version": 1. The type prevents reading one kind of JSON as another. The version gives future changes a way to distinguish formats; it does not automatically migrate every old format.

Follow a scene load

SceneManager::Initialize() calls SceneSerializer::LoadManifest(). Each manifest entry becomes a registered scene factory: a function that can load that scene on request.

When a factory calls Deserialize(), the main steps are:

  1. Read the scene JSON.
  2. Load its explicitly named catalog, if present, including imported catalogs.
  3. Check the type, version, field names, and values.
  4. Parse entity descriptions and expand prefab instances.
  5. Check relationships: duplicate IDs, missing parents, parent cycles, component rules, and exactly one primary camera.
  6. Check that script files exist under the allowed script roots.
  7. Create a new Scene, resolve referenced assets, and attach runtime components.
  8. Evaluate the new scene once with zero elapsed time, then return it or a set of errors.

The temporary description structs in SceneDescription.h are useful here. They hold asset names while validation is underway. The final components hold handles after assets have been resolved.

The zero-time update prepares physics objects and initial transforms/poses without advancing the simulation. Lua startup callbacks wait until the first positive tick.

The serializer restores the previous shared catalog if the load fails. The partially built scene is not installed as the active scene. Asset loading is separately cached, however: a failed scene load is not a promise to undo every resource that was loaded during the attempt.

Errors are addresses into the data

A serialization error contains a source file, a JSON location, and a message. For example:

arena-02.scene.json/entities/player/components/script/path:
Script '.../Scripts/player.lua' does not exist

The slash-separated location tells you where the bad value lives. Some errors use an entity ID in that location; others use an array index. Read it as a route to the problem, rather than assuming every message is a directly executable JSON query.

Strict field checks also catch misspellings such as halfExtent instead of halfExtents. If you add a new component in C++ but forget its parser, the file should fail validation instead of silently pretending the feature loaded.

Prefabs: reusable descriptions

A prefab is a file containing entity descriptions that can be reused. A scene instance names a source file, an instance name, an optional transform, and optional overrides.

This is the shape of an instance inside a scene's prefabs array:

{
  "source": "PhysicsBody.prefab.json",
  "instance": "ball",
  "transform": { "translation": [0, 4, 0] },
  "overrides": {
    "root": { "rigidBody": { "restitution": 0.5 } }
  }
}

The loader expands it into normal scene entities. Names are given an instance prefix so repeated prefabs do not all use the same entity IDs. Nested prefab loads are checked for cycles.

This is load-time reuse. It is not a full live prefab editing system, and placing a Blender collection instance does not automatically create a Haki JSON prefab instance. See the existing physics scene fixture src/Tests/Serialization/Fixtures/Physics.scene.json and prefab fixture src/Tests/Serialization/Fixtures/PhysicsBody.prefab.json for a working pair.

The scene manager's job

The serializer knows how to build a scene. The manager decides which scene is active and when its lifetime starts or ends.

It keeps registered factories, one active scene, one pending request, and transition state. A new pending request can replace the earlier pending request; this is not an unlimited queue.

From C++ code that already has access to the manager, a request looks like this:

auto result = manager.RequestScene("arena-02");
if (result == Haki::SceneRequestResult::UnknownScene)
{
    // Check the registered IDs in Project.json.
}

An accepted request means the manager scheduled it. It does not mean disk loading has already succeeded. GetLastActivationStatus() and GetLastSerializationErrors() describe the later activation result. Requesting the already active scene normally returns AlreadyActive; deliberate reloads use the reloadIfActive option.

The normal scene lifetime is:

factory creates Scene
    → OnLoad
    → OnEnter(payload)
    → repeated OnUpdate / UpdateRuntime / OnRender
    → OnExit
    → OnUnload
    → destruction

For a scene switch, the manager creates the next scene and calls its OnLoad() before removing the old scene. If the factory returns no scene, including when deserialization fails, the old scene remains active. OnLoad() itself has no success/failure return value. Exceptions from custom callbacks are not caught here, so the protected factory-failure path is not a general exception-recovery system.

The optional payload uses std::any, a C++ container for a value whose type is checked later. It could carry scene-entry information. It is not automatically serialized to JSON or available as a Lua scene-switch API.

Transitions

The manager supports instant transitions and timed covering/revealing phases. A fade specification stores durations and a color. Currently SceneManager::Render() only calls the active scene's render function: the transition state alone does not draw a fade overlay. A visible transition needs rendering code to use that state.

Loading is synchronous. A fade duration does not turn scene loading into background work, and switching scenes does not provide spatial world streaming.

What saving means today

The import tool writes scene JSON from Blender exports. The runtime scene serializer is primarily a loader; it does not currently provide a full “save every live entity back to the Blender scene” path.

Project settings have their own save path. ProjectSettings::Save() rereads the latest project JSON, updates settings fields, and uses a temporary file before replacement. This preserves scene registrations and unrelated values that an exporter may have changed meanwhile.

Editor autosave waits for about one second without further settings changes. It saves on clean shutdown when enabled, too. This saves window/render/editor settings, not an entire running gameplay session. Inspector changes to an entity do not become authored Blender changes automatically.

Environment defaults

Omitting environment uses the engine's default environment when that texture exists in the composed catalog. "environment": null explicitly opts out. An environment object selects a texture, intensity, and rotation.

Project rendering settings can hide the visible skybox while leaving environment lighting enabled. Background visibility and lighting are separate choices.

5. Assets and the Blender pipeline

An asset is a reusable resource: a mesh, texture, material, shader, skeleton, or animation clip. An entity is one use of those resources in a scene.

Twenty crates can share one mesh and one material while keeping twenty different positions and physics bodies. Sharing resources saves memory. It does not automatically mean those crates are drawn in one GPU call.

Folder ownership

The engine folder holds general defaults. Shared holds game resources deliberately reused across scenes. A scene folder holds that scene's sources and runtime package. Empty folders are unnecessary.

The asset ownership document Assets/README.md gives the shorter operating rules. Old experiments in Archive/ are outside runtime discovery and packaging.

From Blender to a running scene

  1. Author in Blender. Place kit meshes, lights, camera, and controller. Use the Haki add-on for physics and script properties.
  2. Validate. Catch duplicate IDs, unsupported physics transforms, bad paths, and incompatible components.
  3. Export a GLB. Blender writes models and Haki metadata into the export.
  4. Run the Python importer. It creates or updates the scene JSON, local catalog, imported resources, and receipt.
  5. Run the engine against those files. The serializer creates entities; loaders prepare assets in memory; scene systems create physics and scripting state.

A .blend change alone does not update a running scene. A raw GLB export alone does not necessarily update its scene JSON either. The complete export/import step connects those changes.

Why GLB?

glTF describes models and their related data. A .gltf file commonly refers to separate buffers or images. .glb is the binary container version and can pack that data together. It is a transport format between Blender and the importer/runtime, not the whole Haki project format.

For external formats such as FBX or OBJ, convert_model.py tools/convert_model.py is a separate preparation tool that uses Assimp-supported input to produce a canonical GLB. Runtime loaders still consume the resulting supported data; this is not native runtime loading of every source format. For scenes authored with Haki metadata, use the Blender add-on's export route.

How Haki metadata travels

Blender knows about meshes and cameras, but it does not know what a Haki CharacterControllerComponent is. The add-on stores Haki-specific descriptions in exported custom data, under extras.haki.

This includes stable entity IDs and authored components such as colliders, scripts, and runtime parent relationships. Scene metadata carries scene script and environment choices.

The exporter temporarily writes this metadata, exports visible objects with cameras and lights, and restores previous custom properties afterward. Collider previews are development drawings, rather than extra visible collision meshes that should appear in the game.

The exporter enables Y-up conversion and uses raw lighting conversion so an authored sun strength such as 1 does not become an unexpectedly large imported value.

Why flatten the Blender object tree?

Blender parenting can serve organization, modeling, animation, and gameplay attachment. Preserving all of it blindly would make engine behavior depend on many relationships that have no gameplay meaning.

The importer resolves ordinary object placement into world transforms. Explicit runtime attachments remain as parent components. Skeletons retain the pose hierarchy required by animation.

So a flat list of scene entities does not mean that bones were flattened or that attached visuals cannot follow a player. It means those relationships are represented deliberately.

Catalogs are a resource address book

An entry connects a readable ID to a source and type. This is an actual engine asset entry:

{
  "id": "engine.mesh.unit-cube",
  "type": "mesh",
  "source": "Geometry/UnitCube.gltf",
  "mesh": "UnitCube"
}

The mesh selector identifies which mesh inside the file to use. One model file can contain multiple meshes, skins, and animations, so a source path alone is not always enough.

A catalog can import other catalogs. Scene catalogs import engine and shared resources explicitly. Source paths are relative to the catalog that declares the entry, even when another catalog imports it.

The catalog rejects duplicate IDs, hash collisions, and import cycles. It does not scan every folder and guess what belongs to the scene.

Three stages of an asset reference

Stage Representation Meaning
Authored files String such as engine.mesh.unit-cube Stable logical name
Catalog/runtime lookup 32-bit AssetID derived from the string Compact lookup key
Loaded component Typed handle with slot index and generation Access to a loaded resource

The string is hashed using the catalog's MakeRuntimeId() function. Hashing converts text into a number. Since different strings could theoretically produce the same number, the catalog explicitly checks for collisions.

Why a handle has a generation

Imagine mesh A occupied slot 4. It was unloaded, and mesh B later reused slot 4. An old reference containing only “4” could accidentally access B.

A generation number changes when a slot receives a new resource. The resource manager checks both the slot and generation. An old handle then returns no resource rather than pointing at the replacement.

handle.IsValid() only checks that the handle has a non-invalid index. AssetManager::GetMesh(handle) and the resource manager perform the stronger live-resource check. Do not treat IsValid() alone as proof the resource is still loaded.

What the loaders do

AssetManager maintains managers and loader registries for each asset type. A load request supplies an ID and source. The manager returns an existing resource when that ID is already loaded consistently, or finds a compatible loader and stores its result.

Loader Main work
glTF mesh Read vertex/index data and prepare a GPU mesh
glTF skeleton Build pose nodes, joint order, and bind information
glTF animation Read timed translation/rotation/scale tracks
Material file Resolve shader and texture references; create material parameters
Shader file Read and compile vertex/fragment shader sources
Texture file Decode an image and create its GPU texture

The glTF loaders share a GltfDocumentCache, so reading a mesh, skeleton, and clip from the same model does not require parsing the file independently for every request.

Loading here is synchronous. Several loaders create GPU objects and therefore need the right OpenGL context. An atomic generation counter in the resource manager does not make the whole asset manager thread-safe.

Resource lifetime is separate from scene lifetime

Scenes store handles. The asset manager owns the actual resources globally. Unloading a scene destroys its entities and scene systems, but does not automatically evict every asset those entities referenced.

This supports reuse across scene changes. It also means there is no complete automatic memory-budgeted streaming/unloading policy yet. Adding one would require deciding when resources are no longer needed and how dependencies are kept alive.

Authored and generated files

Treat .blend and Lua files as authored sources. Imported scene JSON, imported materials/textures, and catalog entries are generated by the pipeline.

The importer stages changes and records generated files in ImportReceipt.json. On reimport, it uses that ownership record to replace its own output and preserve unrelated authored files. It refuses unsafe output collisions.

If you hand-edit a generated material, expect a later import to replace it. For a lasting appearance change, change the authored material or establish a separately owned material with its own ID and pipeline reference.

The importer also preserves window, rendering, and editor values in Project.json. Exporting an arena should not reset your project graphics preferences.

6. The renderer

The renderer turns the current scene into an image. It does not decide how the player moves or which attacks deal damage. It receives a camera, lights, environment, and objects to draw.

Haki currently uses OpenGL 3.3 and a forward renderer. Forward means each visible surface is shaded using the lights and material while that surface is drawn. The extra shadow, depth, and post-processing passes do not make this a deferred renderer.

Begin with one triangle

A mesh contains vertices and usually indices. A vertex is a point with data such as position, normal, UV coordinates, and color. An index says which vertex to reuse when forming a triangle.

A normal describes which way a surface faces. A UV is a 2D coordinate used to look up a color or value in a texture. A tangent supplies another surface direction, useful for normal maps.

The CPU prepares buffers and asks the GPU to draw. Two small GPU programs do most of the visible work:

  • The vertex shader positions each vertex. For animated geometry it also applies bone deformation.
  • The fragment shader calculates a candidate pixel's color using the material, textures, lights, and other inputs.

Between them, the GPU fills the triangle's screen area. This is called rasterization. Values such as UVs and normals are smoothly carried across the triangle for the fragment shader to use.

vertex data
  → vertex shader
  → triangles cover screen samples
  → fragment shader
  → depth/blending checks and output

A depth buffer stores how close the visible surface is at each pixel. It prevents a wall behind the player from painting over the player merely because it was submitted later.

Coordinates along the way

For an ordinary vertex, the main transformation is:

clip position = Projection × View × Model × local position

Model is the object's world matrix. View describes the camera. Projection supplies perspective or orthographic projection. The GPU then divides by the clip coordinate's W value and maps the result into the viewport.

This is why a correct mesh can disappear because of a bad camera, an incorrect world transform, or near/far clipping. The mesh file is only one part of its final position.

What a material is

A material combines a shader, parameter values, textures, and drawing rules. A shader is the program; a material supplies that program's inputs for one appearance.

For example, two wooden props can share the same shader but use different base colors or roughness values. MaterialState also controls backface culling, depth testing/writing, blending, and whether the material uses the transmission pass.

The current imported shader is GltfPBR. PBR means physically based rendering: it models roughness, metalness, and light reflection in a reasonably consistent way. A stylized palette texture can still use this renderer. The desired hand-painted/toon art direction does not mean a complete toon-outline and rim-light pipeline is already implemented.

Useful material ideas:

Input What it changes
Base color The main surface color
Roughness Whether reflections look sharp or broad
Metalness Whether the surface behaves like a metal
Normal map Small lighting detail without changing the mesh outline
Emissive Surface brightness that does not depend on incoming light
Alpha Whether a surface is solid, cut out, or blended
Transmission Light/background visibility through a surface

An emissive surface does not automatically become a light that illuminates nearby objects. It can contribute to bloom, which is an image effect.

How the scene submits work

Scene::OnRender() gathers the selected camera, environment, and light components. It calls BeginFrame(), then submits one RenderItem per drawn submesh.

A submesh is a range of a mesh that can be drawn separately, often because it uses a different material. One entity can therefore produce multiple draw calls.

A render item contains mesh and material handles, a world matrix, a submesh index, and optional bone matrices. It does not contain a full entity or Lua script. This keeps the renderer focused on drawing.

The scene then queues Lua canvas drawing, calls Render(), and calls EndFrame(). The renderer borrows a skinned item's joint matrices until those submissions have been processed; the owner must keep them alive during that work.

Preparing the drawing list

The renderer resolves handles, skips unusable submissions, computes bounds, and separates opaque, transmission, and transparent objects.

Frustum culling means skipping geometry outside the camera's view volume. Bounds make this test cheaper than checking every triangle. Off-screen opaque objects can still enter the shadow pass because they may cast a visible shadow.

Skinned meshes currently keep bind-pose bounds, which may be too small once a character moves its limbs. The renderer avoids ordinary frustum culling for these animated submissions rather than incorrectly hiding them.

Opaque items are sorted by shader, material, and mesh to reduce changes in GPU state. Transparent items are sorted mainly from far to near because blending depends on what was drawn behind them.

Sorting is an optimization, not automatic instancing. Reusing a mesh and reducing draw calls are related but separate ideas.

The rendering passes in order

A pass is one stage of drawing, often writing into a particular image rather than directly to the window.

Some stages are disabled by settings or skipped when unnecessary. In words: first prepare visibility and lighting information, draw the scene into a bright-color image, adjust that image for display, then put overlays on top.

1. Directional shadow maps

A shadow map records scene depth from a light's point of view. A surface asks: “Am I farther from the light than the nearest recorded surface?” If yes, something blocks the light.

The renderer uses the first directional light for its shadow direction and splits camera depth into four cascades. Near regions get a more useful share of texture detail than if one map covered the entire world uniformly.

ShadowDistance limits the covered distance. ShadowMapResolution controls map detail. PCF smooths shadow comparisons by sampling nearby texels; PCSS adds a more expensive estimate of softness based on blockers. Neither replaces correct mesh normals or correct light direction.

Drawing into four shadow maps costs extra geometry work. A crate visible once can be drawn again for shadows. The shadow counters help explain why total work exceeds the visible object's single draw.

2. Depth and normal prepass

This stage draws opaque geometry with a simpler shader to record depth and surface direction. SSAO uses those images.

When the depth prepass is enabled, its depth can also be copied to the main target so expensive lighting avoids repeatedly shading surfaces hidden behind other surfaces. The extra pass has its own cost, so measure the result instead of assuming it always helps.

Wireframe mode skips this prepass and SSAO because triangle-filled depth is a poor match for drawing only triangle edges.

3. SSAO

Screen-space ambient occlusion estimates where nearby surfaces block indirect light, using screen depth and normals. It adds contact shading around objects and corners.

It only knows what the current screen buffers contain. It is not full world-space light simulation and cannot discover all hidden geometry.

Sample count, radius, bias, power, half-resolution mode, and blur affect its cost and appearance. Too much strength can make a bright stylized arena look dirty or dark at every prop edge.

4. Opaque lighting and the environment

The main shader combines material values, direct lights, shadows, and indirect lighting. Current light limits per frame are 4 directional, 64 point, and 16 spot lights. Extra lights beyond these arrays are not all processed.

The environment is an HDR image representing surrounding light. The renderer prepares cube maps for the visible environment and filtered versions used for diffuse and rough reflections. This is image-based lighting, or IBL.

Diffuse lighting describes broad surface response. Specular lighting describes reflection. The engine also has ambient sky/ground settings. These controls help fill surfaces that are not facing a direct light.

The skybox is the visible background. It has its own toggle. Turning it off does not require turning off indirect diffuse or specular lighting.

5. Transmission and transparency

The transmission path copies the already drawn opaque scene/background so a transmitting surface can sample what is behind it. This is a screen-based approximation, not ray-traced refraction through arbitrary layers.

Other transparent materials are then drawn with blending. Transparent objects are harder to sort perfectly than opaque ones, particularly when surfaces overlap or intersect. Keep that limitation in mind when designing effects.

6. Bloom, exposure, and tone mapping

The scene is drawn into a floating-point HDR target. HDR allows brightness values greater than 1, so bright lights and emissive surfaces keep useful brightness information before display conversion.

Bloom filters bright parts of the image through smaller images and combines a soft glow. BloomThreshold selects what contributes; BloomIntensity sets how much glow is added.

Exposure scales brightness. An ACES-style tone-mapping curve compresses HDR values into a displayable range. The shader then applies a display gamma conversion. This is why a numeric base color is not necessarily the exact final screenshot color.

Color textures should be read with their color-space meaning intact. Base-color images and data textures such as normals do not have the same interpretation. Accidentally treating a normal map as display color changes the numbers used by lighting.

7. FXAA and overlays

FXAA is a final image filter that softens jagged edges using local contrast. It can reduce aliasing cheaply but may soften fine details too.

Debug lines and the canvas are drawn after scene post-processing. ImGui is rendered after the scene renderer finishes. This helps text remain readable rather than glowing and changing with scene exposure.

What framebuffers and GPU buffers are

A framebuffer chooses where drawing goes. It can point to textures containing color, depth, or other values. Render-to-texture is what makes SSAO, shadows, bloom, and final image filters possible.

A GPU buffer stores data on the GPU: vertices, indices, camera values, light arrays, object transforms, or bone matrices. Uniform buffers group values so shaders can access them consistently. Haki keeps shared camera/light data separate from per-object data.

The wrappers in src/Haki/GL create, bind, move, and release these resources. They hide repeated OpenGL setup; they do not remove the need for a valid context and correct lifetime.

Resolution and cost

Telemetry distinguishes three sizes:

Size Meaning
Window Logical desktop dimensions
Game Actual framebuffer pixels, including display scaling
Render Internal scene target after render-height and render-scale choices

With a 1920×1080 framebuffer, renderHeight = 720, and renderScale = 1, the internal target is 1280×720. A render scale of 0.5 then makes it 640×360. Presentation scales the result to the game framebuffer; canvas overlays use the output viewport.

Lowering render scale reduces pixel work but does not necessarily reduce the number of objects, physics work, or shadow draws. A CPU bottleneck may barely improve.

Reading the counters

SubmittedItems is not the same as DrawCalls. Some submissions are culled or skipped; others produce work in multiple passes. Separate counters track shadows, depth/SSAO, bloom, transmission, canvas, and state changes.

GPU timings arrive a few frames later through timer queries. CPU time around render submission measures CPU work and waiting, not the same thing as pure GPU execution time. Use both rather than treating one number as the whole cost.

7. Physics

Jolt provides collision detection and movement simulation. Haki connects Jolt objects to entities, transforms, Lua callbacks, and Blender-authored data.

The engine uses one PhysicsSystem per scene. PhysicsCore supplies shared Jolt setup, temporary working memory, and a worker-thread pool.

Mesh, collider, and body are separate

A rendered mesh determines what you see. A collider is a simpler mathematical shape used for contact tests. A rigid body describes how that shape moves and responds.

A fence can look curved and detailed while using one or two box colliders. For a small top-down arena, simple collision is often easier to control and cheaper than testing every visual triangle.

Current collider shapes are box, sphere, and upright capsule. This integration does not currently expose general triangle-mesh or convex-hull authoring as another collider type.

Body motion types

Motion type Who moves it? Suitable examples
Static It stays where it was placed unless explicitly repositioned Floor, walls, rock cover
Dynamic Physics integrates velocity, gravity, and collision response A falling prop or knocked object
Kinematic Gameplay supplies a target transform; physics follows it A moving platform or scripted obstacle

Mass affects a dynamic body's response to impulses. Friction resists sliding at contact. Restitution controls bounce. Damping gradually reduces motion. Gravity factor scales gravity for that body.

A mass of zero in the Haki component means use the shape-based default mass calculation, not “an infinitely light dynamic object.”

A sensor detects overlap without acting as a solid obstacle. Bush zones, pickups, and danger zones can use sensors. Sensor behavior and collision layer filtering are separate choices that need to agree.

The JSON parser derives a layer when one is not supplied: sensors use Trigger, ordinary static bodies use Static, and other ordinary bodies use Dynamic. Creating components directly in C++ means you must also choose consistent values there.

Shape sizes

Box halfExtents = [1, 0.5, 2] means a full size of 2×1×4 before transform scale.

A capsule's halfHeight is half its straight middle section, excluding the rounded ends:

total capsule height = 2 × halfHeight + 2 × radius

For radius 0.35 and half-height 0.55, total height is 1.8.

Ordinary collider offsets are local to the entity. Haki applies transform scale to collider dimensions and offsets when creating the shape. A sphere uses the largest scale axis for its radius; a capsule uses the largest X/Z scale for radius and Y scale for height.

The character capsule has a separate rule: its configured dimensions are used directly and its shape is shifted upward so the entity origin is at the feet. Keep the controller transform scale at one and resize the visual separately.

The authoring pipeline rejects mirrored or sheared physics transforms. Shear means a transform has skewed the axes rather than simply rotating and scaling them. Apply or fix these transforms in Blender instead of relying on the runtime's defensive dimension clamping.

Who controls the transform

This is the most important rule when debugging motion:

Object Before the physics step After the physics step
Static body Usually unchanged Remains at its physics placement
Kinematic body Haki reads the entity's target transform Jolt has moved it toward that target during the step
Dynamic body Jolt has its current position and velocity Haki copies active-body position/rotation back to the entity
Character controller Gameplay supplies desired horizontal velocity Collision-corrected position, velocity, and grounded state are copied back

Changing a dynamic body's transform field alone is not a general teleport operation. Physics can overwrite it. C++ has PhysicsSystem::Teleport() to synchronize an explicit transform change with Jolt. The current Lua set_position() writes the transform: character controllers detect it as a teleport, but ordinary rigid bodies do not gain that same behavior automatically.

Static transforms are not continuously uploaded as ordinary movement. Changing collider dimensions after body creation also does not automatically rebuild its Jolt shape. Use the supported live editing methods or reload/recreate the body when changing creation-time properties.

The character controller

The player uses Jolt CharacterVirtual, rather than an ordinary dynamic rigid body. Gameplay requests movement; the controller resolves that movement against surfaces, stairs, slopes, and gravity while remaining upright.

Its minimum component combination is:

Transform + CharacterController

Add Script for Lua movement, or PlayerInput for the built-in movement path. Do not also add RigidBody and Collider to the same controller entity. The controller already owns its capsule and the integration rejects that mixed setup.

The controller has an internal kinematic body so queries and sensors can detect it. The integration keeps that body awake so entering a sensor still produces useful events.

Each update:

  1. Detect an explicitly changed position, such as a respawn.
  2. Read requested XZ movement; the current movement path does not use requested Y velocity as a jump command.
  3. Combine grounded motion or airborne vertical velocity with gravity.
  4. Run Jolt's extended character update, including configured step support.
  5. Copy feet position, actual velocity, ground normal, and grounded state to the components.

Requested speed and actual speed can differ. Pressing into a wall can request 5 m/s while moving almost nowhere. Animation correctly uses the resulting velocity rather than assuming the request succeeded.

Layers decide which pairs are tested

The current collision rules are:

Pair Collides?
Static ↔ Dynamic Yes
Static ↔ Character Yes
Static ↔ Static No
Static ↔ Trigger No
Dynamic ↔ Dynamic Yes
Dynamic ↔ Character Yes
Dynamic ↔ Trigger Yes
Character ↔ Character No
Character ↔ Trigger Yes
Trigger ↔ Trigger No

Characters passing through one another is an explicit game-oriented rule. It does not prevent an attack query from finding a character.

Broad phase is the cheap early search that finds possible nearby collision pairs. Narrow phase tests their actual shapes. Jolt uses these stages internally; Haki supplies the layers and filters that determine eligible pairs.

Queries ask a question without creating a new object

A raycast asks what a line hits first. An overlap sphere asks which shapes intersect a sphere now.

local hit = physics.raycast(vec3(0, 3, 0), vec3(0, -1, 0), 10)
if hit then
    log.info("Ground distance", hit.distance)
end

local nearby = physics.overlap_sphere(self.entity:position(), 2)
for _, other in ipairs(nearby) do
    if other ~= self.entity and other:is_character() then
        -- This is a possible target; gameplay still decides range, team, and damage.
    end
end

These snippets belong inside a script callback. Queries normally exclude the Trigger layer; the optional includeTriggers argument includes it. There is no automatic “ignore the caller” rule in the shown Lua query. Filter self and unsuitable targets in gameplay.

A sphere overlap does not answer whether a wall is between two players, nor whether a target lies in front of the attacker. Add line-of-sight and direction checks when the attack needs them.

Contacts become Lua events after simulation

Jolt can invoke contact listeners on its worker threads. Those listeners queue raw body IDs under a lock. They do not call Lua or modify arbitrary scene components directly.

After the step, Haki resolves IDs to entities and dispatches events on the main scene update path:

Jolt workers detect contact
  → queue raw event
  → physics step completes
  → resolve entities
  → ScriptSystem dispatches callback

Solid events call on_contact_begin/end; sensor events call on_trigger_enter/exit. Entity scripts receive the other entity. Scene scripts receive both entities.

These are contact events, not a full damage system. Do not assume one callback equals one attack or one damage application. Gameplay should track attack windows, targets already hit, or cooldowns as appropriate.

Limits and threading

The default world reserves capacity for 4096 bodies, 4096 body pairs, and 2048 contact constraints. These are configured limits, not benchmark guarantees. The physics system logs capacity problems rather than silently making them disappear.

Physics runs at the fixed simulation step. Jolt uses workers internally, but Lua and ordinary scene mutation remain on the engine's update path. Moving gameplay onto threads requires more than calling it from a Jolt callback.

Removing a rigid body, collider, or controller component triggers registered cleanup hooks. Destroying the scene removes its world and remaining bodies. These hooks are why removing ECS data must also clean up the matching Jolt object instead of leaving an invisible collider behind.

8. Animation

Animation changes the pose of the character's visual mesh. Character movement changes where its controller is in the world. Haki connects them through measured movement speed, but they remain separate jobs.

The pieces

Piece What it means
Skinned mesh A mesh whose vertices can follow joints
Skeleton A hierarchy of pose nodes plus the joints used to deform the mesh
Bind pose The reference pose used when the mesh was attached to the skeleton
Clip Timed changes to node translation, rotation, or scale
Animator Current playback and blending state for an entity
Pose The set of local transforms for the skeleton at one moment
Joint palette The final matrices sent to the GPU to deform vertices

Blender calls the skeleton an armature. A joint often corresponds to a bone, but the imported pose hierarchy may also include non-joint ancestor nodes needed to preserve correct transforms.

The hierarchy is stored parent before child, so the system can build each node's world-within-the-skeleton transform after its parent.

What a clip contains

A walking clip does not store a new full mesh for every frame. It stores keys such as “at 0.2 seconds this node has this rotation.” The runtime finds a pose between those keys.

Interpolation means finding an in-between value. Haki supports:

  • Step: hold the previous key until the next one.
  • Linear: blend positions and scales between adjacent keys; smoothly blend rotations using quaternion interpolation.

The glTF animation loader currently rejects CUBICSPLINE interpolation. Export clips in a supported form instead of assuming every Blender animation curve will load unchanged.

Tracks without a keyed value use the skeleton's bind transform for that part. A named clip in an animator maps to an animation asset handle, so Lua uses a short gameplay name rather than a model file path.

From time to a deformed mesh

AnimationSystem::Update() performs this chain:

  1. Find the skeleton and animator for a skinned mesh.
  2. Advance the current clip or locomotion phase using simulation delta time.
  3. Sample local pose transforms.
  4. Blend poses if a transition is active.
  5. Combine local transforms through the pose hierarchy.
  6. Build final joint matrices using bind information.
  7. Store those matrices on the skinned renderer for rendering.

For each joint, the code combines inverse mesh bind-world, the current global joint pose, and inverse bind matrix. The bind corrections ensure that “no animation” reproduces the reference mesh instead of applying its original placement twice.

You do not need to derive those matrices to play a clip. They become relevant when a mesh explodes, folds incorrectly, or jumps position even though its controller transform looks correct.

How a vertex follows bones

Each skinned vertex has up to four joint indices and weights in the current shader input. A vertex near the elbow can partly follow the upper arm and partly follow the forearm. The GPU combines the selected joint transformations using those weights.

The renderer's current joint palette limit is 128 joints. Check the imported model against that limit; the animation system is not an unlimited-bone renderer.

If a skinned renderer has a valid skeleton but no animator, the system can produce its bind pose. Missing skeleton data clears usable skin matrices instead.

Locomotion uses speed

Locomotion means the repeating movement animation: idle, walk, run. Haki can blend along a one-dimensional speed list. “One-dimensional” just means speed is the input, rather than a larger graph with several inputs.

For example, an authored blend list could associate:

0 m/s → Idle
2 m/s → Walk
5 m/s → Run

At a speed between two samples, the system blends the neighboring poses. It smooths the blend position over time so a small speed change does not jerk the pose. Clips share a normalized phase, helping their movement cycles stay aligned while blending.

The speed comes from the nearest character controller ancestor's actual horizontal velocity. This matters when a wall stops the character: the animation should not run at full speed simply because the movement button is held.

There are also older idle/move settings for simpler scenes. Read LocomotionAnimationComponent and its parser before adding new blend fields; names in Blender, JSON, and C++ are related but not always identical.

MaxPlaybackScale can allow faster playback beyond the final authored speed. It is a playback adjustment, not a root-motion movement system.

Playing an action from Lua

The Lua entity methods can find the entity's animator or an attached child's animator. Clip names must already exist in that animator.

-- Run once when the gameplay action starts.
if self.entity:has_animation("Punch") then
    self.entity:play_animation("Punch", {
        fade = 0.12,
        loop = false,
        speed = 1.0
    })
end

This overrides locomotion for the one-shot. When it finishes, the animator can blend back to locomotion. Avoid calling play_animation every update while a button is held: repeatedly starting an action can prevent it from progressing as intended.

For a pose that should remain at the end:

self.entity:play_animation("Death", {
    fade = 0.15,
    loop = false,
    hold = true
})

Use self.entity:stop_animation(0.2) to return to locomotion with a fade. Without locomotion, stopping freezes clip playback instead.

Useful queries include has_animator(), has_animation(name), animation(), animation_time(), animation_length(name), animation_finished(), and locomotion_speed(). While locomotion owns the pose, animation() reports "locomotion" rather than one fixed clip name.

animation_finished() is a playback state flag, not a guaranteed queued event. Automatic return to locomotion resets it. If gameplay needs a reliable attack window or completion event, design that timing explicitly rather than assuming an animation-event system exists.

Crossfading

A crossfade gradually mixes the previous pose with the new target pose. Haki keeps the last evaluated pose and uses it as the starting pose, then increases the new pose's weight over the fade duration.

Positions and scales are mixed normally. Rotations use quaternion interpolation and choose compatible signs so the blend takes the short rotation path.

This avoids a hard jump between idle and punch. It does not automatically align feet, prevent all sliding, or keep a weapon's hand contact fixed. Those need suitable source animation and, for more advanced behavior, additional systems.

Movement and attacks remain gameplay work

There is no general root-motion path that extracts a clip's travel and moves the character controller through physics. Use in-place locomotion for the current controller workflow. A traveling root in a downloaded clip can move the visual away from its capsule.

Likewise, a fist passing through an enemy in the animation does not automatically deal damage. Gameplay must choose the hit time, query targets, apply rules, and manage repeated hits.

The current system is a clip player with fades and a speed blend. Full animation graphs, layered upper-body masks, inverse kinematics, and a generalized animation-event editor are additional work.

9. Lua gameplay

Lua is where you can change game rules quickly. C++ provides controlled access to engine features; Lua uses that access to build behaviors.

Each scene has its own ScriptSystem and Lua state. Entity scripts run as separate instances inside that shared scene state. They are not separate Lua virtual machines for every entity.

How a C++ binding works

A binding connects a Lua name to a C++ function. For example:

Lua: entity:set_move_velocity(value)
    → C++ binding validates the entity and component
    → writes CharacterControllerComponent.DesiredVelocity
    → the later physics step consumes that request

The Lua call is not a second physics engine. It is a friendlier way to reach the existing engine system. A missing component can therefore produce an error even when the Lua method name is valid.

The API is registered in ScriptBindings.cpp using sol2. Its main groups are vec3, quat, entity methods, scene, physics, input, draw, time, and log.

Anatomy of a script

A behavior file returns a table. The runtime loads that table, creates an instance table for each attached entity, injects self.entity, copies property defaults, and applies authored overrides.

This movement example belongs on an entity with a character controller:

local movement = require("shared.lib.movement")

---@class LearningPlayer : HakiEntityScript
---@field speed number
local Player = { properties = { speed = 5.0 } }

function Player:on_update(dt)
    local direction = movement.camera_relative(
        input.move(), scene.primary_camera()
    )

    self.entity:set_move_velocity(direction * self.speed)
    if direction:length() > 0.001 then
        self.entity:set_rotation(quat.look_rotation(direction))
    end
end

return Player

There is no dt multiplication on the requested velocity. The value is already metres per second; physics applies the time step. For manually integrating a position, position + velocity * dt would need the multiplication.

In Lua, Player:on_update(dt) is shorthand for a function that receives self first. Likewise entity:position() passes the entity as the method's first argument. This is why replacing : with . arbitrarily breaks calls.

Properties become instance fields

properties = { speed = 5 } defines a default. A scene's script component can override it for one entity. During execution, read self.speed.

The supported authored property values are booleans, numbers, strings, and vec3 values. The runtime makes appropriate copies of property values rather than sharing every mutable vector accidentally.

State such as cooldown timers also belongs on self:

function Player:on_start()
    self.cooldown = 0
end

function Player:on_update(dt)
    self.cooldown = math.max(0, self.cooldown - dt)
end

These are separate illustrative callbacks, not additions that should overwrite the movement callback without combining their contents.

Avoid using one mutable module-level variable as if it were private state for every attached entity. A loaded class/module can be shared by several script instances.

Entity scripts and scene scripts

An entity script belongs to one entity. Movement, a crate's health, or a hazard's local behavior fits there.

A scene script belongs to the arena as a whole. Match rules, coordinating a camera, or a shared round timer fits there. It does not receive self.entity; it finds entities through scene queries.

Both are authored through the Blender add-on and exported as paths. Disabling a script in Blender only changes runtime behavior after the relevant export/import updates the scene component.

Callback timing

Callback When it runs Arguments after self
on_start Once when a new instance starts on a simulation update None
on_update Each positive simulation tick Fixed dt
on_contact_begin/end After physics, for solid contact events Other entity; scene script gets both
on_trigger_enter/exit After physics, for sensor contact events Other entity; scene script gets both
on_draw Once per rendered scene frame after the instance has started Render-frame dt, or zero when paused
on_destroy When an entity's running script component is removed/destroyed None

The scene script starts before entity scripts and its update runs before entity updates. Do not rely on a meaningful order between unrelated entity scripts. Coordinate explicitly when one behavior must wait for another's result.

ScriptSystem::Shutdown() clears scene state rather than acting as a guaranteed per-script save callback. Do not use on_destroy as the only way to persist important game data when the entire scene or program exits.

Drawing belongs in on_draw, which receives a temporary canvas context. Calling draw.* from on_update raises an error.

Finding and talking to entities

local player = scene.find("player")
if player and player:valid() then
    log.info(player:name(), player:position())
end

This example assumes the authored stable ID is literally player. Blender-authored IDs are often UUIDs. scene.find_by_name("Player") is convenient for a prototype, but repeated names can make the result ambiguous.

Other helpers include scene.primary_camera(), scene.characters(), and scene.entities_with_script(path). entity:script() returns its running instance table if it has one, allowing game behaviors to call known methods on each other.

Always consider lifetime. A cached entity may have been destroyed. Lua entity methods validate access, but your game should still check optional results and valid() where appropriate.

Lua destruction requests are queued until the current callback batch ends. This avoids destroying registry entries in the middle of the loop that is visiting them. Do not assume destroy() removes the entity in the middle of the very next Lua expression.

Script paths and modules

Scene-local script paths start at the scene's Scripts/ folder:

player.lua
lib/combat.lua

Reusable modules live under Assets/Game/Shared/Scripts:

local movement = require("shared.lib.movement")

The custom require resolves the module, runs it once, and caches its returned value. It supports local modules too, such as require("lib.combat"). Module names use dots; script component paths use relative file paths ending in .lua.

The Lua state opens basic, math, string, table, coroutine, and UTF-8 libraries. It does not expose normal io, os, debug, or package access, and general file-loading helpers are removed. Modules are resolved through Haki's allowed roots. This is controlled gameplay scripting, not a general-purpose shell environment.

Errors and reloads

A callback error is logged with the script path, entity ID when available, callback name, and Lua stack trace. The failing instance is disabled until a successful script reload. This avoids printing the same failure every frame.

The game polls for script changes at roughly half-second intervals when reload is enabled. A successful reload replaces class functions while preserving the instance table. Existing health values, timers, and other fields can remain.

That also means reload is not the same as restarting the scene. Changing a property default or adding initialization in on_start does not necessarily reset existing instances or rerun their startup. Reload the scene when you need fresh state.

Editing an already loaded module causes the system to clear module caches and reload script classes, because those scripts may have captured the module in a local variable. This is broader than reloading only one behavior file.

Shader hot reload is separate and follows shader source files through the asset manager. Meshes, colliders, and imported scene structure do not all gain automatic live reload because scripts do.

Why the IDE understands the bindings

The real implementation is C++. Lua Language Server cannot discover that API just by reading your gameplay files.

tools/lua/library/haki.lua supplies type and method descriptions. .luarc.json tells the editor to include them and use Lua 5.4. These descriptions provide completion and help catch incorrect arguments; they do not implement the engine API.

Never require the definition file in gameplay. Open the repository root in your editor and use LuaLS. A syntax highlighter alone cannot provide the same completion. See the Lua setup guide tools/lua/README.md.

When adding a C++ binding, update the definitions and meaningful tests in the same change. Otherwise the runtime and IDE tell different stories.

Current API boundaries

The runtime currently exposes entity lookup, movement, selected body operations, camera settings, animation, queries, simple drawing, input, logging, and time. It does not expose every C++ function automatically.

For example, a C++ scene-manager feature is not automatically a Lua scene method. General entity spawning, a full UI system, mouse-to-ground aiming, and network commands need their own supported APIs where the current bindings do not provide them.

10. Input, UI, and development tools

There are three separate layers here: input tells the game what the player requested; the canvas draws game overlays; ImGui provides development controls.

Window and input

Window creates a GLFW window and OpenGL context, loads OpenGL functions through GLAD, polls desktop events, and presents frames. It keeps framebuffer dimensions updated when the display changes.

InputManager connects devices to gainput and exposes queries for keyboard, mouse, and gamepads. It also supports C++ action mappings so an action can be associated with a device control.

The main loop polls events and updates input once per rendered frame before simulation. Input has both held state and transition state:

Query Meaning
Down The button is held now
Pressed It changed from up to down in the current input sample
Released It changed from down to up in the current input sample

Held input fits movement. A press edge fits starting an action. Remember that several simulation ticks may share one sampled frame's input, as explained in chapter 2.

Lua examples use lowercase names:

local attacking = input.mouse_down("left")
local dodgePressed = input.key_pressed("space")
local superPressed = input.key_pressed("r")

These queries do not implement attacks, dodges, or supers. Gameplay must connect the intent to cooldowns, movement, damage, animation, and effects.

The underlying C++ input API includes mouse position/delta/scroll and gamepad support. The Lua bindings expose a selected subset. A working C++ mouse query does not imply a Lua ground-aim API already exists.

Camera-relative movement

For the top-angled arena camera, pressing W should usually mean moving toward the top of the screen along the ground.

The movement helper takes the camera's forward vector, removes its vertical part, normalizes it, and builds a perpendicular right vector. Input X/Y values are converted into a world XZ direction from those two vectors.

The built-in controller input combines WASD and the first gamepad's left stick. It limits the resulting input length so diagonal movement does not become faster just because two buttons are held. Its gamepad index is zero-based.

The C++ PlayerControllerSystem runs before Lua. If a character uses both built-in PlayerInput and a Lua movement script, Lua can overwrite the desired velocity. Pick one clear owner for gameplay movement rather than tuning two competing speed values.

Who owns input while editing?

When ImGui owns keyboard or mouse input, the game gates the corresponding gameplay controls. Free-look also stops ordinary player control so WASD can move the development camera.

The debug camera owns a separate pose copied from the gameplay view when activated. It does not move the scene's primary camera component. Its projection override can also show a different view without rewriting the exported camera.

When comparing Blender and runtime framing, choose the gameplay camera and scene projection first. Otherwise you may be comparing an authored camera with a temporary development view.

The canvas

The engine's Canvas queues rectangles, sprites, and text for one frame. The renderer draws them over the finished scene and clears them afterward. This is called immediate-mode drawing: code describes what to draw again each frame, rather than creating a permanent button object once.

Coordinates start at the output viewport's top-left. X increases right; Y increases down. Units are output pixels. Higher layers draw on top, and later calls within the same layer draw on top of earlier ones.

The canvas groups neighboring compatible quads into texture batches to reduce draw calls. A quad is a four-corner shape drawn as triangles. Text becomes a sequence of glyph quads.

Screen HUD versus world labels

A screen HUD stays in a fixed screen position. A world label follows a 3D point, but is drawn at a stable pixel size facing the camera. The latter is often called a billboard.

These are callbacks you could place in a player script:

function Player:on_draw(dt)
    draw.screen_text(20, 20, "Prototype", {
        size = 20,
        color = {1, 1, 1, 1}
    })

    draw.label(self.entity:position() + vec3(0, 2, 0), "Player", {
        size = 18,
        color = {1, 1, 1, 1},
        depth_test = true
    })
end

draw.label projects the anchor point through the current camera. With depth testing enabled, scene geometry covering that anchor can hide the label. It is an anchor visibility test, not a fully simulated 3D text mesh.

The canvas uses display-color values with alpha. It is drawn after scene tone mapping, so changing scene exposure should not act as the main brightness control for the HUD.

Fonts

Font reads a TrueType file and bakes glyphs into an atlas: one texture containing many character images. Drawing text looks up glyph rectangles inside that atlas.

The present font path covers printable ASCII, not a full international text shaping and localization system. Text can be scaled from its bake size, but very large scaling can look soft. This is one reason a complete game UI may eventually need more font and layout support.

ImGui is the development interface

The runtime overlay provides hierarchy and inspector panes, graphics controls, physics debug visibility, pause/step, reload controls, script errors, and project/window settings.

Debug drawing

DebugDraw queues lines and shapes such as boxes and capsules. These help answer “what does the physics system think is here?” or “which bounds are used for culling?”

Collider overlays can distinguish solid bodies, sensors, and characters. A visible mesh may be offset from its collider; showing both makes that error much clearer than guessing from collision behavior alone.

These drawings last one frame unless queued again. They are development graphics, not permanent scene meshes or exported kit assets.

Telemetry: learning where the time goes

Telemetry uses the engine canvas and fonts. It tracks recent average/minimum FPS, frame time, CPU stages, GPU passes, graphics toggles, available GPU memory information, and dimensions.

Milliseconds are often more useful than FPS. A 60 FPS frame has about 16.67 ms total. A 120 FPS frame has about 8.33 ms. Saving 2 ms matters even when the FPS number changes differently at different starting rates.

CPU timings measure work on the main processor. GPU timings measure rendering work through queries and can arrive later. They are not independent values you should always add into one total: CPU and GPU work can overlap.

VRAM reporting depends on what the driver exposes; unavailable data should not be read as zero memory use. Several reported values are smoothed or refreshed periodically, so an overlay is a diagnosis aid rather than a per-instruction trace.

Logging

Logger routes messages to the installed logger; startup uses ConsoleLogger. Lua's log.info/warn/error feeds into the same general reporting path with script context.

Start with the first useful error, not the last visual symptom. A missing material load can cause a skipped draw later. A disabled script instance can make movement stop while rendering and physics remain healthy.

Debug by following the data

Blender looks correct, runtime is wrong

Follow this route:

.blend → exported GLB + metadata → imported scene/catalog → loaded components → system result

At each boundary, ask whether the expected value exists there. If the scene JSON still contains a script disabled in Blender, the problem happened before script execution. If JSON has the right camera but the debug view differs, inspect camera selection and projection override.

Confirm which Assets folder the process opened before changing the code. A source/build-copy mismatch can imitate an importer or renderer bug.

The player does not move

  1. Read the script log. An errored instance is disabled until reload.
  2. Check that the script is attached to the controller entity, not just the armature or visual mesh.
  3. Confirm it has Transform and CharacterController, without an extra rigid body/collider combination.
  4. Check pause state and whether free-look or ImGui currently owns input.
  5. Compare requested movement with actual velocity. Collision can correctly stop a valid request.

entity has no characterController means the API exists but the target entity lacks its required component. Installing editor definitions cannot solve that runtime ownership problem.

The player faces the wrong direction

Separate three questions: is movement world-relative or camera-relative, is gameplay facing using negative Z forward, and does the visual need a local forward correction?

Fixing a model's local orientation should not require rotating every movement vector or making the physics capsule sideways. Keep model correction on the attached visual.

The camera is too far away or has the wrong projection

Inspect the primary camera in scene JSON, then the live camera component, then the active development camera/override. For orthographic views, inspect orthoSize; distance alone does not zoom the picture.

For a gameplay follow issue, inspect the scene's camera script and the tick order. A script might clamp to arena bounds or wait until the player crosses a screen threshold. These are game rules, not automatic SceneManager behavior.

A material is black or unexpectedly dark

Check the material/texture load errors, source paths, normals, backface winding, UVs, light direction/intensity, and environment settings. Disable one rendering effect at a time to isolate the cause.

The canyon shoreline issue is a useful concrete example. The bank and water slab overlapped; combining and recalculating the open mesh could flip bank-top normals downward. Blender's display hid the problem more easily than the runtime lighting did. Correct material colors alone could not repair those normals.

The fix preserved the intended per-part winding. A Blender smoke check now verifies exported top-triangle winding, upward normals after Y-up conversion, and palette UVs. See blender_canyon_water_smoke.py tools/tests/blender_canyon_water_smoke.py. It demonstrates why checking the actual exported geometry is more useful than only judging a viewport screenshot.

An animation looks broken

Check that the mesh, skeleton, and clips agree; named clips exist; interpolation is supported; the visual parent/local transform is correct; and the controller is not being moved by an unintended animated root.

A good capsule position with a displaced mesh points toward the visual/animation path. A good pose that faces sideways points toward local orientation or facing conventions.

Settings revert

Check the loaded project path and autosave state. The runtime persists project settings to the project it opened. Importers preserve those settings, but a different working directory can make you inspect a different Project.json.

Disabling autosave itself must be saved explicitly if you want that preference to survive the next launch. Entity inspector edits and project rendering settings have different persistence rules.

Performance drops

Compare CPU stages and GPU passes before reducing poly count blindly. Try one controlled change: lower internal render resolution, turn off shadows, or pause simulation. Observe which change affects frame time.

If lowering resolution helps a lot, pixel shading/post-processing may matter. If it barely helps, inspect CPU work, object submissions, simulation, and shadow geometry. These observations suggest where to investigate; they do not replace measurement.

Adding a feature across the whole pipeline

Suppose you add a gameplay component that must be authored in Blender. A C++ struct alone is only the first piece.

  1. Define its data and owner. Is it per entity, per scene, or per project? What are its defaults and units?
  2. Implement runtime behavior. Decide which system reads it, when it runs, and which other system owns any shared transform/state.
  3. Define its stored form. Add description/parsing/validation in the serializer. Decide which values are authored and which are runtime-only.
  4. Carry it through import. Update importer metadata handling and exported JSON generation.
  5. Expose authoring controls. Add Blender properties, validation, and metadata export. Update add-on packaging when distributing it.
  6. Expose gameplay access if needed. Add C++ bindings, Lua definitions, and useful inspector controls.
  7. Check the complete route. Test valid data, a useful failure case, export/import, scene load, and visible runtime behavior.
  8. Document the behavior. Include defaults, units, ownership, and persistence rules.

Do not add every layer when the feature does not need it. A local Lua cooldown may need no new component or Blender control. A renderer-wide preference belongs in renderer/project settings rather than an arbitrary scene entity.

  5. Change one renderer setting and explain the pass/timing change.
  6. Add a small engine feature only after you can identify which missing capability requires it.

For the planned online arena game, networking will introduce new questions: which machine owns the authoritative state, how inputs are sent, how clients predict movement, and how corrections are displayed. Fixed-step simulation is useful groundwork, but the present code does not already solve those questions.

Use the current engine to finish a small, measurable local gameplay loop first. The code map and ownership rules in this guide help you place the next feature when that loop exposes a real need.
